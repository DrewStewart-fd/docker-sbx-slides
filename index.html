Why we're here · a scenario

An ordinary afternoon with a coding agent

You ask Claude Code to fix a failing test. To save time you let it run commands without approving each one.

To understand the test, it reads the README of a dependency the test imports. Somewhere in that README is a comment you'd never see on GitHub, because Markdown hides it.

To you it's invisible. To the agent it's just more text in the task, and it reads like an instruction.

The same text could arrive in a GitHub issue, a code comment, a web page the agent fetched, or a poisoned package update.

Why we're here · without SBX

The agent runs as you, so it can do what you can

1

It follows the instruction

One more command in a long run of commands. Easy to scroll past.

2

It reads your secrets

~/.aws/credentials, ~/.ssh, ~/.npmrc, and any GITHUB_TOKEN or ANTHROPIC_API_KEY in your shell.

3

It sends them out

One HTTPS request. Your laptop can reach any server on the internet, so nothing stops it.

4

It leaves something behind

A line added to .git/hooks/pre-commit runs again the next time you commit, long after the session ends.

What you see

A passing test and a tidy summary.

Unless you read every command it ran, nothing looked wrong.

What you lost

Cloud access, Git push rights, package publish rights, and an API key billed to you.

A plain container helps a bit: it only sees what you mount. But it shares your kernel, outbound network is open by default, and whatever you mounted read-write can still be changed.

What it is

A microVM per agent

Each sandbox gets its own kernel, its own Docker Engine, and its own storage. The agent can work with full privileges inside the sandbox and still can't touch your machine.

Inside the sandbox

  • Install packages, run builds
  • Start containers, run Compose
  • Execute whatever the agent decides

The trade-off, in Docker's words

Sandboxes "trade higher resource overhead (a VM plus its own daemon) for complete isolation."

Key framing: we're not limiting what the agent can do, we're limiting where it can do it. Full privileges, tiny blast radius.

Why use it

What you get

Autonomous agents install, build, and execute. That's exactly what you don't want happening directly on your laptop.

Hypervisor isolation

Separate kernel per sandbox. No shared memory or processes with the host.

Credential isolation

A host-side proxy injects API keys. The values never enter the VM.

Network control

Outbound traffic goes through a host proxy with a deny-by-default policy.

Full Docker inside

The agent gets its own Docker Engine, with no path to your host daemon.

Plus visibility: the dashboard and sbx policy log show what the sandbox tried to reach and whether it was allowed.

Five benefits. The fifth, visibility, is the one people underrate: you can see every outbound attempt.

When to use it

Good fits

Autonomous coding agents

Claude Code, Codex, Gemini and others running commands without you approving each one.

Agents that need real Docker

Building images, running containers, Compose.

Unfamiliar code or repos

Try them without risking your host.

Repeatable team setups

Share one environment file or kit so everyone gets the same sandbox.

Background: the same logic applies to any untrusted code, such as third-party model code. The Docker docs frame SBX around coding agents.

If the agent runs in "yolo" / auto-approve mode, it belongs in a sandbox.

Plain English

Whoever controls the kernel controls the machine

A hypervisor creates and runs virtual machines. It decides what CPU, memory, disk, and network each VM gets, and each VM believes it has a whole computer.

Analogy: containers are roommates sharing one apartment with locks on the bedroom doors. A sandbox is a separate apartment. Even if someone picks the lock on their own door, they're still not in yours.

Background example

Loading an untrusted model

Say you pull a model from Hugging Face to try it out. Loading a model normally just reads weights, but trust_remote_code=True tells the library to run Python code shipped inside the model repo, and older pickle weight files can execute code the moment they load.

A malicious repo can use either path to read your cloud credentials, SSH keys, or source code, and send them out. Where that code runs decides how much it can reach.

Your machine

The code runs as you. It can read ~/.aws/credentials, ~/.ssh, and your projects, and it can reach any server on the internet.

Plain container

Better: it only sees what you mount. But it shares your host kernel, outbound network is open by default, and anything mounted read-write can be changed.

SBX sandbox

  • Own kernel, so an exploit lands in the VM
  • Sees only the mounted workspace
  • Outbound goes through the proxy, deny-by-default
  • Your API keys are never inside

Caveat A direct workspace mount is read-write. Use --clone so the agent works on a private copy, and review changes before running anything it touched.

Security model

Five layers of isolation

1 Hypervisor
separate kernel, no shared memory
2 Network
proxied, deny-by-default
3 Docker Engine
its own, not yours
4 Workspace
mounted paths only
5 Credentials
injected on the way out

From the Security page. The primary boundary is the microVM itself; the other four layers ride on top of it.

Credential isolation

The key is added after the request leaves the VM

Docs wording: "credential values never enter the VM." This is what makes prompt-injection credential theft a non-event.

Credential isolation

Storing keys with sbx secret

sbx secret set <service>                    # global by default
sbx secret set <service> --sandbox <name>   # scope to one sandbox
sbx secret ls                               # list stored secrets
sbx secret import                           # import from host env vars
sbx secret rm                               # remove a secret

Supported services

anthropiccopilotcursordevindroidgithubgooglegroqmistralnebiusopenaiopenrouterxai

Dynamic sources

1Password op:// AWS Secrets Manager Host command

Registry credentials for private images and kits stay host-only.

sbx secret import is the quickest on-ramp: it picks up keys already in your shell environment.

Dynamic sources: instead of pasting the key into sbx, you store a pointer to where the key already lives. sbx looks up the real value on the host when the proxy needs it. The sandbox only ever sees a placeholder.

1Password: sbx secret set anthropic --ref 'op://Work/Anthropic/credential'. AWS Secrets Manager: same --ref flag with the secret's ARN. Both need the op or aws CLI installed and signed in on the host.

Host command: sbx secret set github --command 'gh auth token'. sbx runs the command and uses its output.

Why it matters: no second copy of the key to leak, and rotating tokens stay current. Values are cached 55 minutes by default (--refresh 30m or --refresh on-demand to change that), and running sandboxes pick up changes without a restart.

Caveat from the docs: the command text is stored and replayed, so never put a secret inside the command itself.

Network isolation

Deny-by-default, with a log

sbx policy ls                                               # list active rules (--wide shows rule IDs)
sbx policy allow network api.example.com                    # allow a host (comma-separate multiple)
sbx policy allow network --sandbox <name> api.example.com   # one sandbox only
sbx policy deny network ...                                 # deny wins over allow
sbx policy rm network --id <rule-id>                        # remove a rule
sbx policy log                                              # what was allowed and blocked
sbx policy check                                            # would this request be allowed?

Host formats

api.example.com *.example.com example.com:443 IPs CIDR ranges HTTP method + path

Review the defaults

The default allowed domains include broad wildcards. Run sbx policy ls and remove what you don't need.

The docs themselves recommend trimming the default allow list. Good first action after install.

Workspace modes

How code gets into the sandbox

Direct mount

Your folder, read-write. The agent edits your working tree in place.

sbx run claude                       # current folder
sbx run claude ~/Projects/my-repo    # a specific repo
sbx run claude ./my-repo ./docs:ro   # extra folder, read-only

Clone --clone

Your repo stays read-only. The agent commits in its own copy; you fetch the changes or it pushes them.

sbx run --clone claude .                       # clone the current repo
sbx create --clone --name fix-login claude .   # create now, attach later
sbx run --name fix-login

Mountless

Nothing from your Mac is visible. Most isolated; good for throwaway work and unknown code.

sbx create --name scratch claude                  # no path = no mount
sbx run --name scratch                            # attach by name
sbx cp ./src/ scratch:/home/agent/workspace/src   # copy files in

Direct: sbx run with no path mounts the current folder. Extra folders can be added after the first; append :ro to make one read-only.

Clone: the host repo is mounted read-only at /run/sandbox/source and the agent works in a separate writable Git clone inside the sandbox. Its commits are reachable through a git remote named sandbox-<name> on the host. The clone follows whatever branch you had checked out at create time; no branch is created for you. Clone mode has to be chosen at create time, the folder must be a Git repo, and it only works from the main checkout, not a worktree. Removing the sandbox deletes anything not fetched or pushed.

Mountless: only sbx create with no path gives you this, since sbx run with no path mounts the current folder. Name it so you can attach later. The agent starts in /home/agent/workspace. sbx cp needs absolute sandbox paths. Files survive stop and restart and are deleted on sbx rm.

Workspace modes

What still needs your attention

The main risk

In direct mode the agent can change files that run automatically later: Git hooks, CI configs, build files. They run on your Mac, outside the sandbox.

Second trust exception

Shared agent skills are visible across sandboxes. With --skills readwrite, one sandbox could change instructions other sandboxes use.

Default is readonly. Leave it there.

Our practice: branch first

Start every task on its own branch. Changes land there to review or delete. In clone mode the clone starts on that branch too.

git switch -c sbx/<task>   # before you start
sbx run claude
ls .git/hooks              # not covered by the branch
git status                 # untracked files

A branch doesn't cover .git/hooks or untracked files. Check both before running anything the agent touched.

Both risks are called out by Docker in the docs. Clone mode is the default I'd recommend for anything unfamiliar.

Why the branch caveat: .git/hooks lives inside .git, which isn't versioned and is shared by every branch. A rewritten hook survives switching back to your main branch. Untracked files (.env, build output) aren't on any branch either.

Skills: --skills accepts off, readonly (default), or readwrite. Only readwrite lets one sandbox's edits reach others.

Supported agents

Supported agents, and the one we use

Docker Sandboxes supports these agents out of the box:

Claude Code Codex Copilot Cursor Devin Docker Agent Droid Gemini Kiro OpenCode Shell

Shell is an agent-less sandbox for manual setup or testing.

Our setup: Claude Code through Keystone

Our model access goes through the Keystone Bedrock gateway, not direct vendor APIs. The keystone-bedrock-kit mixin points Claude Code at that gateway, so Claude Code is the agent we run.

You can still switch between the Claude models the gateway offers, using /model inside Claude Code.

sbx run claude --kit /path/to/keystone-bedrock-kit/   # our entry point

Outside our environment you'd pick any of these with sbx run <agent>: sbx run codex, sbx run gemini, and so on. Each one talks to its own vendor's API with its own key.

We don't have those keys. Our access is through Keystone, which fronts AWS Bedrock with an Anthropic-compatible endpoint. The kit sets ANTHROPIC_BASE_URL to the gateway, opens the network policy for that host, and has the proxy inject the Keystone token. Claude Code honors ANTHROPIC_BASE_URL, so that's the agent the kit is built for.

The quick start later in the deck walks through installing and running the kit.

Customizing Experimental

Kits package tools and config

A YAML descriptor declares network access, credentials, setup commands, and agent instructions. Reference a kit as a local directory, ZIP, git repo, or OCI image.

Workload kit

Base environment and launch command (an agent or a shell). Passed to sbx run or sbx create.

Mixin kit

Adds tools, configuration, or runtime behavior. Added with --kit, as many as you need.

Stacking kits: one workload, many mixins

# Docker's example: v3 Claude workload + Playwright mixin
sbx run docker.io/docker/sbx-kit-claude:2.1.267 --kit docker.io/sbx/playwright:1.61.1

# Ours: built-in claude + Keystone + another mixin (repeat --kit)
sbx run claude --kit /path/to/keystone-bedrock-kit/ --kit ./team-tools-kit/

# Add a mixin to a sandbox that already exists
sbx kit add my-sandbox ./team-tools-kit/

A kit set bundles a workload and mixins and pins each image digest. sbx kit: pack, push, pull, inspect, sign, provenance, add. v3 kits need sbx v0.45+, and every kit in a sandbox must be v3.

The example pairs a Claude Code workload with a Playwright mixin for browser testing. Authoritative spec: github.com/docker/sandbox-kit-spec.

Stacking: --kit can be repeated, and every --kit must be a mixin. The workload is the agent argument (claude here). ./team-tools-kit/ is a placeholder for whatever mixin your team builds.

Version rule: every kit in a sandbox must be the same generation. Our Keystone kit is schema v2 and rides on the built-in claude workload, so stack it with other v2 mixins. Docker's Playwright example is v3 and pairs with the v3 workload, so it can't be dropped onto our Keystone line as-is.

sbx kit add rebuilds the sandbox container with the new kit appended. Agent session state and the workspace are kept. Sandboxes created before that feature shipped are refused with an error.

Kit arguments: --kit-arg name=value applies to every kit; --kit-arg kit.name=value targets one.

Quick start

keystone-bedrock-kit

A mixin kit that routes Claude Code through Fandango's Keystone Bedrock gateway. Three files: spec.yaml, README.md, .gitignore.

1

Install sbx

brew trust docker/tap
brew install docker/tap/sbx
2

Clone or fork

Fork to make it your own

git clone https://github.com/fandango/keystone-bedrock-kit.git
gh repo fork fandango/keystone-bedrock-kit --clone
3

Validate, store token

Once per machine. Token stays on the host.

sbx kit validate /path/to/keystone-bedrock-kit/
sbx secret set keystone-bedrock-kit
4

Run

Workspace = current dir, or list paths

sbx run claude --kit /path/to/keystone-bedrock-kit/
sbx run claude --kit /path/to/keystone-bedrock-kit/ /path/to/repo

Repo: github.com/fandango/keystone-bedrock-kit. sbx secret set prompts for the Keystone token. It's never written to the repo and never enters the sandbox.

Multiple repos: append more paths after the first.

Quick start

One spec.yaml, four concepts

schemaVersion: "2"
kind: mixinname: keystone-bedrock-kit
displayName: Keystone Bedrock endpoint
permissions:
  network:
    allow:
      - [private-gateway-host]credentials:
  - service: keystone-bedrock-kit
    apiKey:
      name: ANTHROPIC_AUTH_TOKEN
      proxyManaged: true
      inject:
        - domain: [private-gateway-host]
          scheme: bearerenvironment:
  variables:
    ANTHROPIC_BASE_URL: "https://[private-gateway-host]"
A

Mixin

Layers onto the built-in claude workload via --kit

B

Deny-by-default network

Opens the policy for the gateway host only

C

Credential isolation

Host proxy adds the token as a Bearer header. It never enters the VM.

D

Pre-baked config

Points Claude Code at the gateway, not the Anthropic API

Payoff: same setup for everyone, one command, no retyping a base URL, allow rule, or token per sandbox.

Description field trimmed for space. Every block maps to a concept from earlier in the deck.

Quick start

Adapting it for your gateway

Change the hostname in 3 places

  • permissions.network.allow
  • the inject domain
  • ANTHROPIC_BASE_URL

The service name matches the name passed to sbx secret set. Re-run sbx kit validate after any edit.

Why schemaVersion: "2"?

v3 is a build-time format compiled into an OCI image. As of sbx v0.45.1, sbx kit validate on a local directory accepted only schema 1 or 2.

Built-in names like claude select v2 kits. A v3 mixin needs a v3 workload such as docker.io/docker/sbx-kit-claude.

Source for the schema note: comments in the kit's own spec.yaml, cross-checked with the Kits docs.

Assessment

Strengths and trade-offs

Strengths

  • True hypervisor isolation
  • Credentials never enter the VM
  • Deny-by-default network with logging
  • Full Docker for the agent, safely
  • Reusable setups via env files and kits

Trade-offs

  • VM + daemon overhead per sandbox
  • Default allow list has broad wildcards
  • Direct mode can alter auto-run files
  • Shared skills cross sandbox lines in readwrite mode
  • Kits, sbx env still experimental

Every trade-off here has a mitigation already covered: review the allow list, use clone mode, pin kit versions.
